1. # Phase 1 plan: repo foundation for parallel development

Status: draft. Source decisions live in `Architecture.md`. This plan supersedes the "Phase 1: scaffold" step in `docs/plans/trainer-web.md` and the "Next steps" in `Architecture.md` section 11.

## 1. Goal

By the end of Phase 1 the repo contains every deployable and its local infrastructure, so separate people or agents can build the three web apps, the API and the database in parallel without waiting on each other.

Proof that it works: **each of the three apps has a login page, and a user can sign in through each one against the real API and database** (using development authentication, not Cognito). The login page is a landing page with a "Sign in" button (hosted login is the production model, P4); in development the button leads to a dev-only email and password form. After sign-in the app shows a placeholder home page and calls `GET /v1/me`.

Out of scope for Phase 1: real Cognito, any business module (trainers, booking, dispatch, payments, video), deployment to AWS, real-time.

## 2. Starting point

- `apps/client-web` exists. `libs/frontend/ui` has `fc-stack` and `fc-button`.
- Missing: `trainer-web`, `admin-web`, the API, any database, any auth, the API contract, CI.
- `eslint.config.mjs` has `depConstraints` set to `*` (no boundary rules).
- **Docker is not installed** on the development machine.

## 3. Decisions

Agreed: P1, P2, P3, P5 (Docker being installed by the owner), P6. P4 is decided as hosted login.

| # | Decision | Recommendation | Alternative |
|---|----------|----------------|-------------|
| P1 | API contract approach | Contract first: hand-written OpenAPI is the source of truth; frontend types are generated from it; a CI check compares the spec generated by NestJS to it | Code first (NestJS generates the spec): simpler, but the frontends then wait for the backend |
| P2 | ORM (open question 5) | Drizzle ORM with `drizzle-kit` SQL migrations; PostGIS columns via custom types | TypeORM (most integrated with NestJS, weaker typing) |
| P3 | CI platform (open question 6) | GitHub Actions, because the repo is on GitHub | Other |
| P4 | Login pages vs hosted login | **Decided: hosted login for now (D7 unchanged).** Each app's `/login` page is a thin landing page with a "Sign in" button that calls `AuthService.signIn()`. With Cognito that redirects to the hosted login. In development, `DevAuthService` sends the user to a dev-only `/dev-login` route with an email and password form, registered only in non-production builds. A fully custom sign-in can be added later without changing the `AuthService` interface | Custom login pages calling Cognito directly (rejected for now) |
| P5 | Local infrastructure | Docker Compose (Postgres + PostGIS, Redis). Needs Docker Desktop installed | Install Postgres and PostGIS with Homebrew; no Redis until needed |
| P6 | Development authentication | The API issues dev-only JWTs from seeded users via `POST /v1/dev/login`. The same JWT guard validates both dev tokens and (later) Cognito tokens. The dev module is not loaded when `NODE_ENV=production` | Frontend-only fake with no API involvement |

Ports: client 4200, trainer 4201, admin 4202, API 3000, Postgres 5432, Redis 6379, mock API 4010.

## 5. Boundaries (Nx tags)

Tags: `scope:client|trainer|admin|api|shared`, `type:app|feature|data-access|ui|util` for the frontend and shared code, plus `type:api-app|api-lib` for the backend (`apps/api` is `scope:api,type:api-app`; `libs/backend/*` are `scope:api,type:api-lib`; `api-contract` is `scope:shared,type:util`). Rules are implemented in `eslint.config.mjs`.

Constraints to put in `eslint.config.mjs`:
- `type:app` may depend on `type:feature`, `data-access`, `ui`, `util`.
- `type:feature` may depend on `data-access`, `ui`, `util`, never on another feature.
- `type:ui` may depend only on `type:util`.
- `scope:client|trainer|admin` may not depend on each other or on `scope:api`.
- `scope:api` may not depend on frontend libs. Both sides may depend on `libs/shared/api-contract`.
- The existing raw-HTML rule continues to apply; the new apps and `feature-login` must pass it.

## 6. Workstreams

Work starts with one serial foundation step (W0), then runs in parallel (W1 to W7), then a short integration step (W8).

### W0: foundation (serial, first, one owner)
Everything else depends on this. Keep it small.
1. Install Docker (P5), copy `.env.example` to `.env`.
2. Add tag constraints from section 5 to `eslint.config.mjs`. Tag existing projects.
3. Create `libs/shared/api-contract` with the OpenAPI skeleton: `openapi/openapi.yaml` referencing `openapi/paths/*.yaml` and `openapi/schemas/*.yaml`. Phase 1 endpoints: `GET /v1/health`, `GET /v1/me`, `POST /v1/dev/login`. Add scripts to generate TypeScript types (check generator `--help` first) and to lint the spec.
4. Add `docker-compose.yml` and root scripts: `dev:infra`, `dev:api`, `dev:all`, `mock:api` (Prism on port 4010 from the OpenAPI file).
5. Add the CI workflow: install, `nx affected -t lint test build`, with a Postgres+PostGIS service for API tests.
6. Add the dev-server proxy convention: every app calls `/api/v1/...`; `proxy.conf.json` forwards to `API_TARGET` (default `http://localhost:3000`, or the mock on 4010).
- Acceptance: `pnpm nx run-many -t lint build` is green; lint fails on a forbidden cross-scope import; `docker compose up` starts Postgres and Redis; `pnpm mock:api` answers `GET /v1/health`.

### W1: shared UI for login (parallel)
Owner: whoever builds `libs/frontend/ui`. Create, each with a spec and AXE-clean:
- `fc-page` (centered page container), `fc-card`, `fc-heading`, `fc-text`, `fc-alert` (error and info messages)
- `fc-form-field`, `fc-text-input`, `fc-password-input`
- extend `fc-button` with a loading state
- Inputs integrate with Signal Forms (`@angular/forms/signals`).
- Rule: one folder per component, exports added to `src/index.ts` in small separate commits to limit merge conflicts.
- Acceptance: each component's spec covers inputs, outputs, content projection and accessible labelling; lint and tests pass for `ui`.

### W2: auth libs and login page (parallel after W1's form components exist; the interface can start earlier)
- `libs/frontend/auth`: `AuthService` interface (`signIn()`, `signOut()`, `user` signal, `accessToken()`), `DevAuthService` that completes sign-in through `POST /v1/dev/login`, `authGuard`, `roleGuard(role)`, HTTP interceptor adding the bearer token, token storage (memory plus session storage). The real Cognito implementation (hosted login, OIDC, `angular-oauth2-oidc`) is a later phase.
- `libs/frontend/feature-login`: one `LoginPage` (a landing page with a "Sign in" button) and a `DevLoginPage` (email and password form, exported through a separate entry point that production builds never register), both built only from `fc-*` components. Configuration through route data: `{ title, expectedRole, redirectTo }`. Wrong-role sign-in shows a clear error ("this account is not a trainer").
- `libs/frontend/data-access`: API client typed from the generated contract types.
- Acceptance: unit tests for guards, interceptor and the login page (success, wrong credentials, wrong role, loading state).

### W3: API foundation (parallel)
- Generate `apps/api` with `@nx/nest` (check `--help` for options). Global prefix `/v1`, validation pipe, error filter, structured logging, CORS allow-list, Swagger at `/docs`, health endpoint.
- `libs/backend/common`: config module (env validation), JWT guard that picks its verifier from config: dev HS256 secret now, Cognito JWKS later; roles decorator and guard.
- `libs/backend/identity`: `GET /v1/me`; `POST /v1/dev/login` (loaded only outside production); user and role model.
- Acceptance: integration tests for health, `/me` with valid, expired and missing tokens, role guard; contract check passes (Nest-generated spec matches `openapi.yaml`).

### W4: database (parallel with W3; W3 consumes it)
- `libs/backend/database`: Drizzle setup (P2), `DatabaseModule`, migration scripts (`db:generate`, `db:migrate`), seed script.
- Initial schema: `users` (id, cognito_sub nullable, email unique, display name, role, created_at). PostGIS extension enabled in the first migration. Roles: `client`, `trainer`, `admin`.
- Seed (dev only): one user per role with a documented dev password hash used only by the dev login.
- Acceptance: `pnpm db:migrate && pnpm db:seed` works from an empty database; migrations run in CI.

### W5, W6, W7: the three apps (parallel, same recipe)
Apps: `client-web`, `trainer-web`, `admin-web`. `client-web` already exists, so the recipe is: copy its pattern.
For each of `trainer-web` and `admin-web` (check generator `--help` first):
1. Generate with prefix `fc`, tags `scope:<name>,type:app`, port 4201 / 4202.
2. Apply the styling setup (`.postcssrc.json`, `styles.css`, Material theme in the build `styles`), as documented in `Architecture.md` section 7.1.
3. Add `proxy.conf.json` and wire it into `serve`.
4. Routes: `/login` (lazy `feature-login` with route data), `/dev-login` (only added when the environment is not production), `/` (placeholder home behind `authGuard` and `roleGuard`), wildcard redirect.
5. The placeholder home shows the signed-in user from `GET /v1/me` using `fc-*` components only, and a sign-out button.
6. Differences between apps are limited to route data (title, expected role) and a placeholder shell; no duplicated login code.
- For `client-web`: add the same routes and replace the current demo home page.
- Acceptance per app: lint (including the raw-HTML rule), unit tests, production build, and the login flow works against the mock server first and the real API once W3 and W4 land.

### W8: integration and e2e (serial, last)
- `apps/e2e` with Playwright: for each app, sign in with the seeded user of the right role, see the home page; sign in with the wrong role, see the error; sign out.
- Wire `pnpm dev:all` to start infra, API and all three apps.
- Update `Architecture.md` (decisions P1 to P6, section 11 next steps) and `README.md` with the run instructions.
- Acceptance: CI green on a pull request, including e2e; a fresh clone runs with `pnpm install`, `cp .env.example .env`, `pnpm dev:infra`, `pnpm db:migrate`, `pnpm db:seed`, `pnpm dev:all`.

## 7. Dependency graph

```
W0 foundation ──┬─> W1 shared UI ──┬─> W2 auth + login page ──┬─> W5 client-web ──┐
                │                  │                          ├─> W6 trainer-web ─┤
                ├─> W3 API ────────┴──────────────────────────┴─> W7 admin-web ───┼─> W8 integration + e2e
                └─> W4 database ──> (W3 consumes)                                  │
```

- W1, W3 and W4 can start as soon as W0 is merged.
- W5 to W7 can start their scaffolding right after W0 and use the Prism mock until W3 and W4 land; they need W1 and W2 to finish the login page itself.
- Everything meets in W8.

## 8. Rules for parallel work

- One branch per workstream, merged by pull request. Use separate git worktrees so streams do not share a working directory.
- Known conflict hotspots and how to avoid them:
  - `libs/frontend/ui/src/index.ts`: add one export line per component; rebase before merging.
  - `pnpm-lock.yaml`: resolve by re-running `pnpm install`, never by hand-editing.
  - `openapi.yaml`: kept as a thin file that only references per-domain files.
  - `eslint.config.mjs`, `nx.json`: owned by W0 only; other streams request changes through W0.
- Contract changes go through a pull request that edits the OpenAPI files first. Frontend and backend both pull from it.
- Every stream keeps `pnpm nx affected -t lint test build` green before merging.

## 9. Risks

- **Docker is missing.** Without it the database and CI service setup cannot be tried locally. Install Docker Desktop first or use Homebrew Postgres+PostGIS (P5).
- **Dev authentication leaking into production.** Mitigation: the dev module is only imported when `NODE_ENV !== 'production'`, with a test that fails if the dev login route exists in a production-mode app.
- **Contract drift.** Mitigation: the CI check comparing the NestJS-generated spec to the hand-written one, plus generated frontend types that fail the build on mismatch.
- **Hosted login limits (P4).** Cognito's hosted page has limited branding and no custom flows. Accepted for now. Revisit if branding, phone login or social login become requirements.
- **Shared UI as a bottleneck.** All three apps wait on the same library. Mitigation: W1 starts immediately after W0 and ships the login components first, in small merges.
- **Tooling versions.** Angular 22, Nx 24 and TypeScript 6 are new; some plugin generators may lag. Check each generator with `--help` before use and expect small manual fixes.

## 10. Definition of done for Phase 1

- Three Angular apps, the API, the database and Redis run locally with documented commands.
- Each app has a working login page built only from shared components, signing in against the real API.
- Boundary rules and the raw-HTML rule are enforced by lint.
- The OpenAPI contract is the source of truth and is checked in CI.
- CI runs lint, tests and builds for affected projects, and the e2e login tests.
- `Architecture.md` reflects the decisions made.
